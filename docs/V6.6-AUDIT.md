# V6.6 — Audit de consolidation et durcissement

Audit réalisé par lecture directe du dépôt tel qu'il est aujourd'hui (branche `main`, après V6.5) — pas par supposition à partir d'analyses antérieures. Classement : 🔴 CRITIQUE, 🟠 IMPORTANT, 🟡 AMÉLIORATION, 🟢 BON (ne pas toucher). Chaque point 🔴/🟠 a été corrigé dans cette même session, sauf mention contraire explicite.

## A. IndexedDB / Dexie

### 🔴 Écriture métier + historique non atomiques (corrigé)
Les 30 fonctions `saveX()`/`toggleXActive()`/`markComplete()`/`trashX()`/`restoreX()`/`purgeX()` des 6 modules faisaient deux écritures Dexie indépendantes : l'enregistrement métier, puis `addHistory()`. Si la seconde échouait après le succès de la première, l'entité changeait d'état réel **sans que son historique le reflète** — la divergence exacte que la mission demande de traiter. `docs/V6.2-C-IMPLEMENTATION.md` §6 documentait ce risque comme "acceptable" sans le corriger ; ce jugement est **révisé** ici.

**Corrigé** : `withHistoryTx(tables, fn)` (`js/core/history.js`) enveloppe chaque paire écriture-métier + `addHistory()` dans une transaction Dexie (`db.transaction("rw", ...)`). Un échec de l'une annule l'autre. Appliqué aux 30 call sites (6 modules × 5 fonctions).

### 🔴 Import JSON et effacement complet non atomiques (corrigé)
`importFile()` (mode "remplacer") vidait puis réécrivait jusqu'à 7 tables (6 modules + historique) comme une suite d'opérations Dexie indépendantes ; `clearDatabase()` de même. Un échec à la 4ᵉ table sur 7 laissait la base à moitié importée/effacée, sans moyen de le détecter ni de revenir en arrière.

**Corrigé** : les deux fonctions enveloppent désormais l'intégralité de leurs écritures dans une seule `db.transaction("rw", [...toutes les tables], async () => {...})` — un échec annule tout.

### 🟠 Absence de verrou anti-double-clic/double-soumission (corrigé)
Aucun bouton de formulaire n'était désactivé pendant l'enregistrement ; aucune action à un clic (archiver, terminer, mettre à la corbeille, restaurer, purger) n'était protégée contre un second déclenchement pendant que le premier était encore en cours. Un double-clic sur "Enregistrer" pouvait créer deux fiches dupliquées (deux `uid()` différents pour la même intention) ; un double-clic sur "Terminer" pouvait écrire deux entrées d'historique identiques.

**Corrigé** : `withSubmitLock(form, run)` (formulaires, désactive les boutons submit) et `withActionLock(key, run)` (actions à un clic, clé par enregistrement+action) — voir `js/utils.js`. Appliqués aux mêmes 30 call sites.

### 🟠 6 fonctions sans `try/catch` du tout (corrigé)
`toggleArchive` (requests.js), `toggleScheduleActive`, `toggleClocherActive`, `togglePersonnelActive`, `toggleIntentionStatus` n'avaient **aucune** gestion d'erreur — un échec Dexie y aurait été une exception non interceptée, sans aucun message à l'utilisateur (pire que le cas "erreur techniquement ignorée" que la mission demande d'éviter : ici, rien n'était même journalisé côté application). Corrigé en même temps que l'atomicité ci-dessus.

### 🟢 Index/schéma Dexie
`js/db.js` : 6 versions successives (5 à 10), toutes additives, jamais de modification rétroactive — vérifié par lecture complète du fichier, cohérent avec `docs/DATABASE.md`. `deletedAt` volontairement non indexé (filtrage en mémoire, volume raisonnable pour un secrétariat paroissial) — décision déjà documentée et toujours valide, non remise en cause.

### 🟡 Comportement après changement de version (non traité)
Aucun test n'a été fait (ni ne peut l'être sans navigateur) du comportement Dexie si un utilisateur ouvre une base créée par une version *plus récente* de l'app avec une version *plus ancienne* du code (`VersionError`). Le catch générique de `main.js` afficherait un message peu spécifique. Risque faible (scénario de retour en arrière volontaire, rare) — laissé pour plus tard.

## B. Historique et corbeille

Repris scénario par scénario (mission section 4) :

| Scénario | Statut |
|---|---|
| Création | ✅ historisé, transactionnel (voir A) |
| Modification | ✅ historisé, transactionnel |
| Mise à la corbeille | ✅ historisé, transactionnel, jamais de suppression réelle |
| Restauration | ✅ même id, transactionnel |
| Suppression définitive | ✅ transactionnel, historique conservé (décision déjà prise en V6.2.c, confirmée) |
| Modification d'un élément déjà en corbeille | **Impossible par construction**, vérifié : `showXForm`/`showXDetail` ne cherchent que dans `state.X` (actifs) ; la vue Corbeille (`js/trash.js`) n'expose que Restaurer/Purger, aucun bouton Modifier |
| Restauration après modification | Sans objet (la modification pendant la corbeille est impossible, voir ci-dessus) |
| Import / fusion | ✅ `deletedAt` préservé (V6.2.c/V6.3), import maintenant transactionnel (voir A) |
| Suppression/restauration en masse | **Non implémenté** — aucune sélection multiple n'existe dans l'UI ; pas de besoin démontré, volontairement non ajouté (éviter la fonctionnalité artificielle) |
| Opération annulée par erreur (ex. purge validée par erreur) | Pas d'annulation possible après une purge — comportement voulu (suppression définitive), le texte de confirmation est déjà explicite ("IRRÉVERSIBLE") |
| Erreur pendant l'opération | ✅ try/catch + rollback transactionnel partout (voir A) |
| Historique lui-même | Une entrée `history` sans entité correspondante (après une purge) est **normale et volontaire** — le rôle d'un journal d'audit est de survivre à l'entité qu'il décrit ; le diagnostic d'intégrité (voir D) l'exclut donc délibérément pour ne pas produire un faux positif à chaque purge |
| Cohérence historique/état réel | ✅ résolu par `withHistoryTx` (voir A) |

## C. Intégrité des données (références croisées)

Les 3 relations existantes (`personId`, `clocherId`, `personnelId` — confirmées exhaustives par grep, inchangées depuis V6.2.a) étaient déjà protégées côté affichage (`findLinked`/`linkedRecordFieldHTML`, V6.2.c) : un lien vers une fiche en corbeille ou définitivement supprimée s'affiche distinctement plutôt que de planter ou de disparaître silencieusement. **Manquant, ajouté** : rien n'agrégeait ce repérage à l'échelle de toute la base — il fallait ouvrir chaque fiche une par une pour découvrir un lien cassé. Nouveau `js/diagnostics.js` (bouton Paramètres "Vérifier l'intégrité des données") : liens orphelins, valeurs hors vocabulaire contrôlé (`STATUS`/`PRIORITIES`/`REQUEST_TYPES`/…), dates invalides, doublons probables (heuristique nom+prénom+date de naissance). ## I. PWA / hors-ligne

### 🟠 Risque de mélange de fichiers entre deux versions du cache (corrigé)
`caches.match(event.request)` (sans précision de cache) interroge tous les caches de l'origine, pas seulement `CACHE_NAME`. Pendant la fenêtre où l'ancien et le nouveau cache coexistent (entre `skipWaiting()` et la fin du nettoyage dans `activate`), une requête pouvait être servie depuis l'ancien cache au lieu du nouveau — exactement le risque que la mission demandait de vérifier ("une nouvelle version ne doit pas laisser l'utilisateur avec un mélange incohérent"). **Corrigé** : lecture explicitement restreinte à `caches.open(CACHE_NAME)`.

- 🟢 `CACHE_NAME` déjà incrémenté à chaque ajout de fichier précaché (vérifié tout au long de cette session : v5 → v7). `activate` supprime déjà les anciens caches. `skipWaiting()`/`clients.claim()` : choix assumé (mise à jour immédiate plutôt qu'attendre la fermeture de tous les onglets), cohérent avec une petite app à itération rapide — non remis en cause.

## K. Tests

67 → **78 tests** (`tests/pure-functions.test.js`), tous passants. 11 nouveaux tests pour `js/diagnostics.js` (`isInvalidDateValue`, `checkReferenceIntegrity`, `checkEnumValues`, `checkPossibleDuplicates`).

**Limitation assumée, pas contournée** : les transactions Dexie (`withHistoryTx`, l'import atomique, l'effacement atomique) ne sont **pas** couvertes par un test automatisé — cela demanderait un vrai navigateur ou un polyfill IndexedDB (`fake-indexeddb`), qui introduirait la première dépendance du projet (même si limitée aux tests, jamais chargée par `index.html`). **Décision** : ne pas l'ajouter unilatéralement — le projet est explicitement "zéro dépendance", et la mission demande de ne pas transformer le projet sans nécessité démontrée. Recommandation posée à l'utilisateur plutôt que tranchée seule : si une couverture automatisée de ces transactions devient nécessaire, `fake-indexeddb` (pur JS, aucune étape de build) est l'option la plus cohérente avec l'esprit du projet.

## M. Qualité du code

- 🟡 Duplication mécanique assumée : les 30 call sites `withHistoryTx(...)` + `withActionLock(...)`/`withSubmitLock(...)` répètent la même structure module après module plutôt qu'une fonction générique unique "sauvegarder une entité" — **choix délibéré** : chaque module garde son vocabulaire, ses messages et son comportement propres (ex. `toggleScheduleActive` réutilise `archive`/`restore`, pas un mot dédié) ; une abstraction plus poussée economiserait des lignes mais rendrait chaque module moins autonome à lire isolément, contraire à l'esprit du projet ("un module = un fichier autosuffisant").
- 🟢 Pas de fonction trouvée nécessitant un découpage pour cette raison seule ; pas de code mort trouvé lors des relectures de cette session.
