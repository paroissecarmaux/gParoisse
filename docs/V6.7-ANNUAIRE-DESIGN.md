# V6.7 — Conception de l'Annuaire (Personnes & Organisations)

**Phase de conception uniquement.** Aucun code n'a été modifié pour produire ce document. Aucune ligne de `js/db.js` n'a changé, aucune donnée n'a été touchée, aucun écran n'a été retouché. Tout ce qui suit est une analyse du dépôt tel qu'il existe réellement au moment de la rédaction (branche `main`, après V6.6), pas une reconduction d'une ancienne analyse.

## 1. Objectif

Remplacer le concept actuel de « Membres » (module Personnes, `people`) et sa séparation étanche avec « Personnel » (`personnel`) par un modèle d'**Annuaire** unique où une même identité (personne ou organisation) peut porter **plusieurs rôles simultanément** (ex. membre du registre + bénévole + contact), sans dupliquer la fiche ni recréer un identifiant à chaque changement de rôle.

## 2. État actuel — ce qui existe réellement

Vérifié par lecture directe du code (pas par mémoire d'une analyse antérieure) :

### 2.1 Deux tables Dexie totalement indépendantes

```js
// js/db.js (v10, courant)
people:     "id, nom, prenom, updatedAt"
personnel:  "id, nom, prenom, typeEngagement, active, updatedAt"
```

Aucun champ ne relie une entrée `people` à une entrée `personnel`. Ce sont deux annuaires parallèles, sans identifiant partagé. **C'est la cause racine du problème posé par la mission** : un prêtre qui est à la fois inscrit au registre paroissial et membre du clergé doit aujourd'hui exister comme **deux fiches distinctes, sans lien entre elles**, avec nom/téléphone/email ressaisis deux fois.

### 2.2 `people` — déjà un embryon de « rôle », mais binaire et non cumulable

```js
// js/people.js
function createDefaultPerson() {
    return { id: "", prenom: "", nom: "", profileType: "paroissien", rgpd: false };
}
function isParoissien(p) {
    return (p.profileType || "paroissien") === "paroissien";
}
```

`profileType` ∈ `{"paroissien", "contact"}` — un choix **exclusif**, pas cumulable. Quand `profileType === "contact"`, `savePerson()` **vide explicitement** tous les champs sacramentaux (`isContact ? "" : $("#...").value`) : un contact ne peut jamais aussi être un paroissien sans perdre son historique sacramentel s'il change de type.

Champs actuels de `people` (`js/settings.js`, `csvFields` de `DATA_MODULES`) : `id, profileType, prenom, nom, dateNaissance, lieuNaissance, dateDeces, telephone, email, adresse, pere, mere, rgpd, registre, lieuBapteme, diocese, anneeBapteme, numeroBapteme, dateBapteme, parrain, marraine, temoin, dateCommunion, lieuCommunion, dateConfirmation, lieuConfirmation, dateMariage, lieuMariage, conjoint, role, groupe, notes, deletedAt`.

Deux champs à noter particulièrement :
- **`role` et `groupe`** (texte libre, section "Groupes & engagements" de la fiche) : un embryon **non structuré** de ce que l'Annuaire doit formaliser. Rien ne contrôle leur contenu, ils ne pilotent aucun badge ni aucun filtre.
- **`rgpd`** : un unique booléen "Consentement RGPD obtenu (conservation des données personnelles)" — masqué en formulaire pour les contacts (`class="paroissial-only"` en CSS, forcé à `false` par le code pour `profileType === "contact"`) : ce consentement est donc **conceptuellement attaché au fait d'être au registre**, pas à l'identité en général, même s'il vit aujourd'hui au niveau de l'enregistrement entier.

### 2.3 `personnel` — un deuxième modèle de rôle, tout aussi non cumulable entre lui et `people`

```js
// js/constants.js
const PERSONNEL_TYPES = ["Bénévole", "Salarié"];
const PERSONNEL_ETATS = ["Laïc", "Prêtre", "Diacre", "Religieux(se)"];
```

Deux axes déjà présents, mais figés en un **seul champ chacun** (pas de cumul possible entre "Bénévole" et "Salarié" pour la même personne, ni de suivi de plusieurs engagements successifs) : `typeEngagement` (engagement) et `etat` (statut canonique). Champs : `id, prenom, nom, typeEngagement, etat, fonction, telephone, email, adresse, dateDebut, dateFin, notes, active, deletedAt`.

### 2.4 Relations existantes (exhaustif, revérifié par grep)

| Champ | Table porteuse | Pointe vers | Obligatoire ? |
|---|---|---|---|
| `personId` | `requests`, `intentions` | `people.id` | Non (chaîne vide acceptée) |
| `clocherId` | `requests`, `schedule`, `intentions` | `clochers.id` | Non |
| `personnelId` | `intentions` (célébrant) | `personnel.id` | Non |

`schedule` (Annonces) ne référence **aucune** personne, uniquement un clocher — vérifié, pas d'exception cachée. `clochers` ne référence non plus **aucune** personne (pas de "responsable de clocher" aujourd'hui).

Comportement actuel à la suppression/restauration (V6.2.c, `js/utils.js` `findLinked()`) : mettre `people`/`personnel` à la corbeille **ne modifie jamais** `personId`/`personnelId` sur les demandes/intentions qui les référencent ; l'affichage distingue déjà "actif" (lien cliquable), "en corbeille" (badge non cliquable "— dans la corbeille"), "introuvable" (définitivement supprimé). **Ce mécanisme est générique et sera réutilisé tel quel pour l'Annuaire.**

### 2.5 Un champ `contact` qui n'a **aucun rapport** avec `profileType: "contact"`

Piège terminologique à ne pas reproduire dans l'Annuaire : `requests.contact`/`intentions.contact` sont des champs texte libre (téléphone/email), pré-remplis depuis la personne liée au moment de la sélection (`person.telephone || person.email`) mais **jamais resynchronisés** ensuite — une copie figée, pas une relation vivante. Rien à voir avec le rôle "Contact simple" de `people.profileType`. L'Annuaire doit choisir un vocabulaire de rôle qui ne recoupe pas ce mot déjà utilisé ailleurs avec un sens différent (voir §7 — le rôle est appelé "Contact simple" pour lever l'ambiguïté à l'écran, mais le risque de confusion textuelle reste à surveiller dans la doc utilisateur de V6.8).

### 2.6 Historique, corbeille, recherche, diagnostic — usage actuel exact

- **Historique** (`js/core/history.js`) : `entityType` vaut `"person"` pour `people` et `"personnel"` pour `personnel` — deux valeurs distinctes dans `ENTITY_TYPES`/`ENTITY_TYPE_LABELS` (`js/constants.js`). Chaque module appelle `addHistory("person"|"personnel", id, action, description)` séparément.
- **Corbeille** (`js/trash.js`) : `TRASH_ENTITY_CONFIG` a deux entrées séparées, `person` → `state.peopleTrash` et `personnel` → `state.personnelTrash`, chacune avec ses propres `restore`/`purge`.
- **Recherche globale** (`js/search.js`) : deux sources séparées, `people` (label "Membres") et `personnel` (label "Personnel"), chacune avec sa propre fonction `search`/`title`/`subtitle`/`open`.
- **Diagnostic d'intégrité** (`js/diagnostics.js`, V6.6) : `checkReferenceIntegrity()` vérifie séparément les liens `personId` (vers `state.people`/`peopleTrash`) et `personnelId` (vers `state.personnel`/`personnelTrash`) ; `checkEnumValues()` vérifie `typeEngagement`/`etat` (personnel uniquement, `people.profileType` n'est **pas** vérifié aujourd'hui) ; `checkPossibleDuplicates()` ne compare que les entrées `people` entre elles — **un doublon personne/personnel (le cas exact du prêtre du registre) n'est aujourd'hui jamais détecté**, alors que c'est précisément le problème que l'Annuaire doit résoudre.
- **Import/export** (`js/settings.js`, `DATA_MODULES`) : `people` et `personnel` sont deux entrées séparées du registre, chacune avec ses propres `csvFields`. Le format de sauvegarde JSON structuré (V6.3) les inclut comme deux clés distinctes sous `data`.
- **Autres dépendances trouvées** (grep exhaustif sur tout le dépôt, pas seulement les fichiers cités par la mission) : `overview.js` (KPI "Membres" = `state.people.length` uniquement, anniversaires du jour = `state.people` uniquement — **`personnel` n'apparaît nulle part dans le Tableau de bord**), `agenda.js` (aucune référence directe à une personne, seulement à des clochers), `people.js: createIntentionForPerson()` (raccourci "nouvelle intention" depuis une fiche Personne, **sans équivalent côté Personnel** pour créer une intention en tant que célébrant — asymétrie qui trahit deux modules pensés séparément).

## 3. Problèmes du modèle actuel

1. **Duplication d'identité** : un prêtre inscrit au registre doit exister deux fois (`people` + `personnel`), sans lien, avec resaisie et risque de divergence (téléphone mis à jour d'un côté, pas de l'autre).
2. **Rôles non cumulables** : `profileType` (people) et `typeEngagement`/`etat` (personnel) sont chacun un choix exclusif, alors que la réalité paroissiale est cumulative (bénévole ET salarié ET registre).
3. **Vocabulaire non structuré parallèle** : `people.role`/`people.groupe` (texte libre) anticipent le besoin sans le formaliser.
4. **Rien ne détecte le doublon personne/personnel** aujourd'hui (diagnostic V6.6 limité à l'intérieur de chaque table).
5. **Aucune place pour une organisation** (fournisseur, association) — forcer une organisation dans `prenom`/`nom` serait sémantiquement faux et activerait à tort des fonctionnalités personne (anniversaire, certificats de baptême…).
6. **Tableau de bord incomplet** : le Personnel est invisible du Tableau de bord aujourd'hui, symptôme direct de la séparation en deux modules non unifiés.

## 5. Modèle conceptuel cible

### 5.1 Type d'entité : `person` vs `organization`

**Recommandation : les deux, avec `entityType` discriminant, comme pour `history` (précédent déjà éprouvé dans ce dépôt).**

| | Avantages | Inconvénients |
|---|---|---|
| Tout en `person` (une organisation = une "personne" sans prénom) | Un seul type à gérer partout | Sémantiquement faux (une SARL n'a pas de date de naissance) ; active à tort les fonctionnalités "personne" (anniversaire, certificats) ; oblige à mettre la raison sociale dans `nom` en pretendant qu'il n'y a pas de `prenom`, fragile |
| `person` / `organization` distincts | Chaque type ne porte que les champs qui le concernent ; le diagnostic peut vérifier des règles différentes (ex. une organisation ne devrait pas avoir de `dateNaissance`) ; correspond exactement au besoin exprimé (fournisseur = personne OU organisation) | Une petite complexité de branchement dans l'UI (formulaire différent selon le type) — déjà maîtrisée dans ce dépôt (ex. `profileType` bascule déjà l'affichage du formulaire Personne aujourd'hui) |

**Recommandation retenue : `entityType: "person" | "organization"`**, conditionnant uniquement les champs d'identité propres à chaque type (voir §5.4), pas les rôles (une organisation peut être `fournisseur` ou `association` ; un rôle comme `clerge`/`salarie`/`benevole`/`registre` n'a de sens que pour `entityType: "person"` — à valider par le formulaire, pas par le schéma).

### 5.2 Rôles — liste retenue, chacun justifié

Format retenu : **liste cumulable**, chaque rôle étant un objet (pas une simple chaîne — justification en §5.5), ex. :

```js
roles: [
  { type: "registre", active: true, dateDebut: "1998-04-12" },
  { type: "benevole", active: true, dateDebut: "2019-01-01", domaine: "Catéchisme" },
  { type: "contact", active: true }
]
```

| Rôle | Définition | Pourquoi il existe | Cumulable avec | Rôle ou relation ? |
|---|---|---|---|---|
| `registre` | Inscrit au registre paroissial (sacrements suivis) | Mission légale/canonique du secrétariat — remplace `profileType: "paroissien"` | Tous | Rôle (statut propre à la personne) |
| `clerge` | Prêtre, diacre, religieux(se) | Statut canonique distinct, pilote des champs propres (affectation, diocèse) — remplace `personnel.etat != "Laïc"` | Tous (un prêtre peut aussi être `registre`, `salarie`) | Rôle |
| `salarie` | Employé rémunéré de la paroisse | Suivi RH minimal (fonction, dates) — remplace `personnel.typeEngagement === "Salarié"` | Tous | Rôle |
| `benevole` | Engagement bénévole dans un service | Suivi de l'engagement (domaine, dates, actif/inactif) — remplace `personnel.typeEngagement === "Bénévole"` | Tous | Rôle |
| `contact` | Simple contact dans l'annuaire, sans autre rôle | Couvre le cas "quelqu'un à joindre" sans en faire un paroissien ou un engagé — remplace `profileType: "contact"` ; **rôle plancher** : une entrée sans aucun autre rôle porte au moins celui-ci | Tous (souvent seul) | Rôle |
| `fournisseur` | Fournit un bien/service à la paroisse | Besoin explicite de la mission — personne ou organisation | Tous | Rôle |
| `association` | Association partenaire (souvent une organisation) | Besoin explicite de la mission | Tous, mais n'a de sens réel que pour `entityType: "organization"` (contrainte de formulaire, pas de schéma) | Rôle |

**Volontairement écarté** : un rôle générique `partenaire` — aucun comportement distinct démontré par rapport à `fournisseur`/`association`, aurait été une catégorie "parce qu'elle semble possible", pas parce qu'un besoin réel l'exige (règle explicite de la mission). Si un besoin précis apparaît plus tard (ex. suivi contractuel), l'ajouter reste additif — pas un choix irréversible à faire maintenant.

**Statuts canoniques (`etat`, aujourd'hui `PERSONNEL_ETATS`) et "diacre/religieux(se)"** : deviennent des **champs spécifiques au rôle `clerge`** (`etatCanonique: "Prêtre" | "Diacre" | "Religieux(se)"`), pas des rôles séparés — un diacre n'est pas cumulable avec "prêtre" pour la même personne, c'est une valeur unique d'un même axe, pas une liste de rôles indépendants.

### 5.3 Identité / Rôle / Relation — la distinction demandée

**Identité** (vit sur l'entrée elle-même, indépendante des rôles) : nom, prénom (personnes) ou raison sociale (organisations), téléphone, email, adresse, notes générales, dates de création/modification, `deletedAt` (corbeille).

**Rôle** (vit dans l'objet du rôle, apparaît/disparaît avec lui) : tout ce qui n'a de sens que **parce que** l'entrée porte ce rôle précis — ex. `fonction`/`service` (salarié), `domaine` (bénévole), `affectation` (clergé).

**Relation** (un lien vers une AUTRE entrée de l'annuaire, ou vers une autre table déjà existante) — analysée cas par cas plutôt que transformée systématiquement en rôle, comme demandé :

| Exemple de la mission | Analyse | Modélisation retenue |
|---|---|---|
| "Cette personne travaille pour telle paroisse" | La paroisse est unique dans cette application (un seul `parishName` en réglages) — la relation est triviale/universelle, pas la peine de la modéliser | Aucune (déjà vrai par construction) |
| "Cette personne appartient à tel clocher" | Relation réelle et déjà modélisée ailleurs dans l'app (`clocherId` existe sur `requests`/`schedule`/`intentions`) | Champ `clocherId` **sur l'objet du rôle concerné** (ex. affectation d'un `clerge` ou d'un `benevole` à un clocher), réutilise `findLinked()` tel quel |
| "Cette personne est responsable de telle association" | Relation dirigée entre deux entrées d'annuaire (une personne, une organisation) — un vrai besoin de relation, pas un rôle | Champ `contactPersonId` **sur l'organisation** (pas une table de relations séparée — voir §11) |
| "Cette organisation fournit tel service" | Descriptif, pas une relation vers une autre entité | Champ libre `categorie`/`notes` sur l'organisation, pas une relation |
| "Ce prêtre est affecté à telle paroisse" (une AUTRE paroisse, ex. prêtre extérieur ponctuel) | L'app ne modélise pas "d'autres paroisses" comme entités — créer cette notion serait hors sujet pour une app mono-paroisse | Champ texte libre (ex. "Paroisse d'origine") sur le rôle `clerge`, pas une relation structurée |

**Principe retenu** : une relation ne devient un champ structuré (`clocherId`, `contactPersonId`) que lorsqu'elle pointe vers une entité **déjà modélisée** dans l'application ; sinon, un champ texte libre suffit — pas de nouvelle table "relationships" générique tant qu'un besoin réel de relations multiples/complexes n'est pas démontré (voir §11).

### 5.4 Données communes (identité)

| Champ | `person` | `organization` |
|---|---|---|
| `id` | ✅ | ✅ |
| `entityType` | `"person"` | `"organization"` |
| `nom` | Nom de famille | Raison sociale (champ unique, pas de `prenom`) |
| `prenom` | ✅ | — |
| `telephone`, `email`, `adresse` | ✅ | ✅ |
| `notes` | ✅ | ✅ |
| `roles` | ✅ (liste, voir §5.2) | ✅ (limité en pratique à `fournisseur`/`association`) |
| `dateNaissance`, `dateDeces`, `lieuNaissance`, `pere`, `mere` | ✅ (identité, pas un rôle — voir remarque ci-dessous) | — |
| `createdAt`, `updatedAt`, `deletedAt` | ✅ | ✅ |

**Remarque sur la filiation** (`pere`/`mere`) et l'état civil (`dateNaissance`/`lieuNaissance`/`dateDeces`) : bien qu'ils ne servent aujourd'hui qu'aux personnes du registre, ce sont des faits d'état civil **de la personne elle-même**, pas du rôle "registre" — une personne garde sa date de naissance même si elle n'a jamais été inscrite au registre (ex. un fournisseur individuel). Classés en identité, pas en données de rôle — contrairement aux champs sacramentaux (§5.5) qui, eux, n'existent que **parce que** le registre paroissial les demande.

### 5.5 Données spécifiques aux rôles

Modélisation retenue : `roles: [{ type, active, dateDebut, dateFin, ...champs propres }]` — un **objet par rôle**, pas une simple chaîne (voir comparaison en fin de section).

| Rôle | Champs propres | Justification |
|---|---|---|
| `registre` | `rgpd` (bool), `lieuBapteme`, `diocese`, `anneeBapteme`, `numeroBapteme`, `dateBapteme`, `parrain`, `marraine`, `temoin`, `dateCommunion`, `lieuCommunion`, `dateConfirmation`, `lieuConfirmation`, `dateMariage`, `lieuMariage`, `conjoint` | Repris tels quels de `people` (aucun champ inventé) ; **déplacés** de l'identité vers ce rôle — un `contact` n'aura plus 15 champs sacramentaux vides |
| `clerge` | `etatCanonique` (Prêtre/Diacre/Religieux(se)), `affectation` (`clocherId`, optionnel), `diocese`, `dateDebut`, `dateFin` | Reprend `personnel.etat` (hors "Laïc", qui devient l'absence de ce rôle) |
| `salarie` | `fonction`, `service`, `dateDebut`, `dateFin` | Repris de `personnel.fonction`/`dateDebut`/`dateFin` |
| `benevole` | `domaine` (ex. "Catéchisme", "Accueil"), `dateDebut`, `dateFin` | Repris de `personnel.fonction` (renommé `domaine`, plus parlant pour un engagement bénévole) |
| `contact` | *(aucun champ propre)* | Rôle plancher, uniquement les données d'identité suffisent |
| `fournisseur` | `categorie` (texte libre ou petite liste, ex. "Fleuriste", "Imprimeur"), `notes` | Repris du besoin exprimé ; **pas de SIRET par défaut** (mission : "si réellement pertinent" — non démontré pour une petite paroisse, à ajouter plus tard si un vrai besoin comptable apparaît) |
| `association` | `categorie`, `contactPersonId` (si l'association elle-même est une organisation ayant un référent humain) | Repris du besoin exprimé |

**Comparaison des deux approches de structuration des rôles :**

| | `roles: string[]` (exemple donné par la mission) | `roles: [{type, ...}]` (retenu) |
|---|---|---|
| Simplicité de lecture | Maximale | Légèrement plus verbeux |
| Dates de début/fin indépendantes par rôle (ex. bénévole 2015-2020 PUIS salarié 2020-…) | Impossible sans un second objet parallèle (`roleData`) — retombe de facto sur la même complexité | Natif, un objet = un cycle de vie |
| Actif/inactif par rôle (ex. bénévole retraité mais toujours registre) | Impossible sans structure annexe | Natif (`active` par rôle) |
| Historique propre à chaque engagement (plusieurs périodes de bénévolat) | Non supporté sans redesign | Supporté nativement (plusieurs objets du même `type` si nécessaire, ou un seul objet mis à jour) |

**Recommandation : `roles: [{type, active, dateDebut, dateFin, ...}]`.** Le gain (dates/statut indépendants par rôle, déjà un besoin réel exprimé par la mission pour bénévole/salarié) dépasse le léger surcoût de verbosité, et évite d'inventer une structure parallèle `roleData` qui recréerait la même complexité sous un autre nom.

## 6. UX proposée

### 6.1 Une seule page "Annuaire", pas plusieurs pages par rôle

Puisque les rôles sont cumulables, une personne peut légitimement devoir apparaître dans plusieurs "pages par rôle" à la fois — la même contrainte que l'app connaît déjà et résout par des **filtres rapides sur une liste unique** (voir `state.peopleQuickFilter`/`filterPeopleByKpi()` dans `js/people.js`, déjà en production). Réutiliser ce patron exact plutôt que d'en inventer un nouveau :

- Sidebar : un seul point d'entrée **"Annuaire"** (remplace "Membres" et "Personnel").
- KPI cliquables en haut de la liste, comme aujourd'hui : "Toutes les entrées", "Registre", "Clergé", "Salariés", "Bénévoles", "Contacts", "Fournisseurs", "Associations", "Organisations" — chaque clic filtre la même liste (pas une page séparée par rôle).
- Chaque carte affiche ses badges de rôle, à la manière des badges déjà utilisés partout dans l'app (`.badge`, styles déjà existants en CSS) :

```
Marie Dupont
📞 06 XX XX XX XX
[Registre] [Bénévole] [Contact]
```

### 6.2 Fiche détail

Une seule fiche par entrée, avec :
- Un en-tête identité (comme aujourd'hui pour Personne/Personnel).
- Une section par rôle actif (accordéon, à la manière de l'existant `.side-accordion` de la fiche Personne), affichée uniquement si le rôle est présent — pas de champs vides à parcourir pour un simple contact.
- Un bouton "Ajouter un rôle" / "Retirer ce rôle" **qui ne recrée jamais l'entrée** — même id, même historique, même corbeille.
- Historique et suppression (corbeille) **au niveau de l'entrée entière**, pas par rôle — retirer un rôle est une simple modification (historisée comme `update`), pas une suppression.

### 6.3 Formulaire

Un formulaire par `entityType` (personne / organisation), avec une zone "Rôles" où l'on coche/décoche les rôles applicables ; cocher un rôle révèle ses champs propres (même mécanique que `updateProfileTypeFields()`/`.paroissial-only` aujourd'hui, généralisée à N rôles au lieu de 2 profils exclusifs).

## 7. Architecture technique proposée

### 7.1 Comparaison des structures de tables Dexie

| Approche | Simplicité | Migration | Recherche/historique/corbeille | Cohérence Dexie |
|---|---|---|---|---|
| `people` / `organizations` / `roles` / `relationships` (4 tables normalisées) | Complexe : toute lecture doit "joindre" manuellement plusieurs tables (IndexedDB n'a pas de jointure native) | Migration en 4 étapes, risque d'incohérence entre tables | 4 surfaces à unifier au lieu d'1 | Mauvaise — reproduit exactement le problème actuel (`people`/`personnel` séparés) à plus grande échelle |
| Une seule table `directory` avec `entityType` + `roles: [...]` embarqué | Simple : une lecture, un enregistrement complet | Une seule table à peupler, un seul id à préserver par entrée | Un seul point de vérité pour historique/corbeille/recherche/diagnostic | Excellente — même patron que `history.entityType`, déjà éprouvé dans ce dépôt depuis V6.2.c |

**Recommandation : table unique `directory`.** C'est le choix qui *résout* le problème actuel (deux tables non reliées) au lieu de le reproduire sous une forme normalisée. IndexedDB/Dexie est un magasin de documents, pas une base relationnelle — un modèle en 4 tables jointes irait à contre-courant de l'outil et de tout ce qui a fonctionné jusqu'ici dans ce dépôt (`clocherId`, `personId`, etc. sont déjà de simples champs id, jamais des tables de jointure).

### 7.2 Forme d'un enregistrement `directory`

```js
{
  id: "uuid",
  entityType: "person",             // ou "organization"
  prenom: "Marie", nom: "Dupont",   // organization : nom seul (raison sociale)
  telephone: "", email: "", adresse: "",
  dateNaissance: "", dateDeces: "", lieuNaissance: "", pere: "", mere: "", // person uniquement
  notes: "",
  roles: [
    { type: "registre", active: true, dateDebut: "", rgpd: false, lieuBapteme: "", /* ... */ },
    { type: "benevole", active: true, dateDebut: "2019-01-01", dateFin: "", domaine: "Catéchisme" }
  ],
  createdAt: "", updatedAt: "", deletedAt: null
}
```

## 8. Impact Dexie

Aucune migration exécutée dans cette phase (V6.7). Pour V6.8 :

```js
// v11 (exemple, additif — ne modifie aucune version existante)
db.version(11).stores({
    // ... toutes les tables v10 inchangées ...
    directory: "id, entityType, updatedAt"
    // `roles` n'est PAS indexé : filtrage en mémoire (state.directory.filter(...)),
    // même principe que deletedAt depuis V6.2.c — le volume d'une petite
    // paroisse ne justifie pas un index sur un champ tableau.
});
```

`people` et `personnel` restent déclarées dans `db.version(11)` **à l'identique** (Dexie exige de relister toutes les tables, mais rien n'y change) — elles ne sont simplement plus lues par le nouveau code. Aucune suppression de table, aucune perte de données possible même en cas d'échec de la migration applicative (voir §9).

## 9. Stratégie de migration (conception seulement, exécution en V6.8)

Principe directeur : **les id ne changent jamais**. Une entrée `people`/`personnel` devient une entrée `directory` **avec le même id**, jamais un nouvel id généré. Conséquence directe et essentielle : **`requests.personId`, `intentions.personId`, `intentions.personnelId` continuent de pointer vers un id valide sans qu'aucune donnée de `requests`/`intentions`/`schedule` n'ait besoin d'être modifiée.** Seul le code de résolution change (chercher dans `state.directory` au lieu de `state.people`/`state.personnel`).

### 9.1 Transformation

- Chaque `people` → une entrée `directory` (`entityType: "person"`, même `id`), `roles: [{type: "registre", ...champs sacramentaux...}]` si `profileType === "paroissien"`, sinon `roles: [{type: "contact"}]`.
- Chaque `personnel` → une entrée `directory` (`entityType: "person"`, même `id`), rôles dérivés de `typeEngagement`/`etat` : `salarie`/`benevole` selon `typeEngagement`, plus `clerge` si `etat !== "Laïc"` (avec `etatCanonique: etat`).
- **Aucune fusion automatique** entre une entrée issue de `people` et une entrée issue de `personnel`, même en cas de nom identique : un rapprochement automatique risquerait de fusionner à tort deux personnes différentes portant le même nom (homonymie). Les deux id d'origine, distincts par construction (UUID aléatoires, collision non réaliste), deviennent deux entrées `directory` séparées.
- **Détection, pas fusion** : le diagnostic d'intégrité (déjà doté d'une heuristique de doublon nom+prénom+date de naissance, V6.6) est étendu pour comparer aussi les entrées issues de `people` et de `personnel` entre elles — signalant "Le prêtre Jean Martin (registre) et Jean Martin (clergé) sont peut-être la même personne", à vérifier et fusionner **manuellement** (nouvel outil de fusion à concevoir en V6.8/V6.9, pas en V6.7).

### 9.2 Ce qui est préservé sans aucun changement

- Identifiants (`id`) — jamais régénérés.
- Références (`personId`, `personnelId`) — jamais réécrites.
- Historique — les entrées existantes (`entityType: "person"` / `"personnel"`) restent lisibles telles quelles ; seules les **nouvelles** entrées (post-migration) utilisent `entityType: "directory"`. Résolution à la lecture, comme le fait déjà `historyEntityType()` pour les entrées pré-V6.2.c.
- Corbeille — un enregistrement déjà en corbeille (`deletedAt` renseigné) dans `people`/`personnel` migre vers `directory` avec son `deletedAt` intact.
- Export/import — voir §12.

### 9.3 Données ambiguës

- Une personne avec `people.role`/`people.groupe` (texte libre existant) : conservé tel quel dans `notes` (ou un champ `ancienRoleLibre` temporaire) — **jamais interprété automatiquement comme un rôle structuré**, faute de vocabulaire fiable pour le faire sans erreur.
- Un `personnel.etat === "Laïc"` sans `typeEngagement` reconnu : migre avec les rôles qu'il a réellement (aucun rôle inféré au-delà de ce que les champs disent explicitement).

## 10. Historique

Voir §4/§9.2. Résumé : entrées existantes jamais réécrites ; nouvelles entrées `entityType: "directory"` ; `historyEntityType()`/`historyEntityId()` étendues pour reconnaître aussi les anciennes valeurs `"person"`/`"personnel"` et les résoudre contre `directory`.

## 11. Corbeille

`TRASH_ENTITY_CONFIG` (`js/trash.js`) passe de deux entrées (`person`, `personnel`) à une seule (`directory`), avec `titleOf` unifié (`${prenom} ${nom}` ou raison sociale selon `entityType`). `trashX()`/`restoreX()`/`purgeX()` deviennent des fonctions uniques sur `directory` au lieu de deux jeux de fonctions dupliquées — une **simplification** du code existant, pas un ajout de complexité.

Relation "responsable d'association" (§5.3) : si l'organisation responsable est mise à la corbeille, le champ `contactPersonId` reste inchangé (même principe que `personId`/`clocherId` aujourd'hui) — `findLinked()` s'applique sans modification.

## 12. Import/export

- **JSON** : `data.directory` remplace `data.people` + `data.personnel` dans le format structuré (V6.3). `detectBackupPayload()` (`js/core/backup.js`) doit reconnaître une sauvegarde V6.8+ (`data.directory`) et une sauvegarde V6.0–V6.7 (`data.people` + `data.personnel`) — à la lecture, un import d'ancienne sauvegarde reconstruit `directory` **par la même transformation qu'en §9.1**, jamais l'inverse. `formatVersion` passe à `2` pour marquer ce changement de forme (le format `1` de V6.3 reste lisible).
- **CSV** : décision à prendre en V6.8, deux options viables — (a) un unique CSV `directory` avec une colonne `roles` sérialisée (ex. `"registre;benevole"`), ou (b) conserver des exports CSV **filtrés par rôle** (ex. "Export CSV Bénévoles") générés depuis la même table, plus proches de l'usage tableur actuel. Pas de recommandation tranchée ici — à évaluer avec un vrai fichier d'export en V6.8.

## 13. Recherche

Une seule source `GLOBAL_SEARCH_SOURCES` (`directory`) remplace les deux sources `people`/`personnel`. Les résultats restent groupés visuellement (le panneau de recherche globale groupe déjà par source aujourd'hui — `renderGlobalSearchResults()`), avec un sous-titre indiquant les rôles actifs plutôt qu'un groupe "Membres" séparé d'un groupe "Personnel".

## 14. Diagnostic d'intégrité

- `checkReferenceIntegrity()` : les vérifications `personId`/`personnelId` ciblent désormais `state.directory`/`state.directoryTrash` (une seule paire de tableaux au lieu de deux) ; nouvelle vérification possible — un `intentions.personnelId` qui pointe vers une entrée sans aucun rôle `clerge`/`salarie`/`benevole` (une incohérence de rôle, pas seulement de référence).
- `checkEnumValues()` : étendue pour vérifier que chaque `roles[].type` appartient au vocabulaire contrôlé, et que les champs propres à un rôle (ex. `etatCanonique`) restent dans leur liste connue.
- Nouvelle vérification : entrée avec `roles: []` (aucun rôle) — cas normalement impossible si le formulaire impose au moins `contact` par défaut, mais utile pour détecter une donnée importée incohérente.
- `checkPossibleDuplicates()` : étendue pour comparer **toutes** les entrées `directory` entre elles (plus seulement `people`) — c'est ce qui permettra, après migration, de repérer les doublons personne/personnel hérités de l'ancien modèle (voir §9.1).

## 15. Tests

Fonctions pures à tester dès que le code de migration existera (V6.8) :
- `personToDirectoryEntry(person)` / `personnelToDirectoryEntry(personnel)` : transformation pure, testable exhaustivement (cas `paroissien`, `contact`, chaque combinaison `typeEngagement`/`etat`).
- `hasRole(entry, roleType)` / helpers de filtrage par rôle.
- `detectBackupPayload()` (déjà pure, V6.3) : étendre les tests existants pour couvrir la clé `data.directory` (nouveau format) et la reconstruction depuis `data.people`/`data.personnel` (ancien format).
- Diagnostic étendu (`checkReferenceIntegrity`/`checkEnumValues`/`checkPossibleDuplicates`, déjà purs et déjà testés en V6.6) : nouveaux cas de test pour les vérifications ajoutées en §14.

## 16. RGPD

- Aucune nouvelle catégorie de donnée personnelle introduite par le regroupement lui-même — les mêmes champs qu'aujourd'hui, réorganisés.
- Les organisations ne sont **pas** des données personnelles au sens RGPD (personnes morales), sauf le champ `contactPersonId` qui pointe vers une personne déjà comptabilisée ailleurs (pas de duplication de données personnelles sur l'organisation elle-même).
- Le consentement RGPD (`registre.rgpd`) reste spécifiquement attaché au rôle registre — cohérent avec sa signification actuelle ("conservation des données personnelles" au sens du registre paroissial), pas étendu artificiellement à un consentement global.
- **Volontairement non ajouté** : SIRET, données bancaires, ou tout champ "fournisseur" à caractère comptable/légal — non demandé par un besoin réel, éviterait de transformer l'annuaire en ERP (contrainte explicite de la mission).
- Export JSON complet contenant `directory` : même niveau de risque qu'aujourd'hui (déjà deux tables incluses), pas une aggravation — les avertissements déjà en place (`docs/BACKUP.md`, `docs/RGPD.md`) restent valables tels quels.

## 17. Risques

| Risque | Sévérité | Mitigation prévue |
|---|---|---|
| Fusion automatique erronée de deux personnes homonymes | Élevée si mal gérée | Pas de fusion automatique — détection + fusion manuelle uniquement (§9.1) |
| Perte de champs `people.role`/`groupe` (texte libre) pendant la migration | Moyenne | Conservés tels quels dans `notes`, jamais interprétés automatiquement |
| Régression du Tableau de bord (KPI "Membres") | Faible | KPI à redéfinir explicitement en V6.8, testé manuellement avant diffusion |
| Volume de travail V6.8 sous-estimé (6+ surfaces à adapter) | Moyenne | Recommandation de sous-phaser V6.8 (voir §19), comme cela a déjà été fait pour V6.2.a/b/c |
| Confusion terminologique "contact" (rôle) vs `requests.contact` (champ texte) | Faible | Déjà identifiée (§2.5), à surveiller dans les libellés d'écran de V6.8 |

## 18. Alternatives étudiées

- **Garder deux tables mais ajouter un id de liaison** (`personnel.linkedPersonId`) : rejeté — ne résout pas le cas général (une organisation fournisseur n'a pas de "personId" à lier), et perpétue la duplication de code entre deux modules quasi identiques.
- **Table `roles` séparée (many-to-many)** : rejeté pour V6.8 (voir §7.1) — complexité de jointure disproportionnée pour le besoin réel ; resterait une option si un jour une personne devait cumuler un très grand nombre de rôles avec des historiques indépendants complexes (non démontré aujourd'hui).
- **Table `relationships` générique** : rejetée pour V6.8 (voir §5.3) — les deux seules relations concrètes identifiées (affectation à un clocher, référent d'une organisation) se modélisent très bien avec de simples champs id, comme le reste de l'application le fait déjà.

## 19. Recommandation finale

Table unique `directory` (`entityType: person|organization`), rôles cumulables sous forme d'objets (`roles: [{type, active, dates, champs propres}]`), relations modélisées au cas par cas en champs id simples plutôt qu'en table générique, migration additive préservant tous les id existants, ancien format de sauvegarde toujours lisible. C'est le choix qui prolonge directement les patrons déjà éprouvés dans ce dépôt (`history.entityType`, `findLinked`, corbeille générique V6.2.c) plutôt que d'en introduire de nouveaux.

## 20. Plan V6.8 (proposé)

Vu l'ampleur (nouvelle table, migration, 6+ surfaces transverses à adapter), **recommandation de sous-phaser**, comme cela a déjà été fait pour la corbeille généralisée (V6.2.a/b/c) :

- **V6.8.a** — Fondations : `db.version(11)` (table `directory`), fonctions de transformation pures (`personToDirectoryEntry`/`personnelToDirectoryEntry`) et leurs tests, migration exécutée au démarrage (peuple `directory` depuis `people`+`personnel`, idempotente — ne re-peuple pas si déjà fait), `directoryRepository.js`.
- **V6.8.b** — Module Annuaire : nouvelle page liste/détail/formulaire unifiée, badges de rôle, filtres par rôle (réutilisant le patron `quickFilter` existant), historique/corbeille branchés sur `directory`.
- **V6.8.c** — Intégration transverse : recherche globale, diagnostic d'intégrité étendu, import/export JSON+CSV, Tableau de bord (KPI redéfinis), retrait des raccourcis clavier/menus pointant encore vers `people.js`/`personnel.js`.

Chaque sous-phase : un commit par changement cohérent, tests après chaque étape, comme la convention déjà établie dans ce dépôt.

## 21. Plan V6.9 (proposé)

- Validation manuelle complète en navigateur (pas d'environnement disponible pendant le développement, comme pour V6.2.c/V6.3/V6.5/V6.6) : migration sur un jeu de données réel, vérification qu'aucune référence n'est cassée, export/réimport d'une sauvegarde post-migration.
- Outil de fusion manuelle de deux entrées `directory` détectées comme doublons probables par le diagnostic (§9.1) — un besoin direct de la migration, pas une fonctionnalité générique ajoutée par anticipation.
- Nettoyage : une fois la migration validée en conditions réelles, envisager (décision utilisateur, pas automatique) de retirer `people.js`/`personnel.js`/les tables `people`/`personnel` du code actif — **jamais des données déjà écrites**, seulement du code mort si le modèle est confirmé stable.
- Mise à jour finale de `docs/ARCHITECTURE.md`, `docs/DATABASE.md`, `README.md`.

## 22. Réponses aux critères de réussite (V6.7 §15)

1. **Une entrée d'Annuaire** = une identité (personne ou organisation) avec un ou plusieurs rôles.
2. **Personne vs organisation** : `entityType`, détermine les champs d'identité (prénom/nom + état civil vs raison sociale), pas les rôles disponibles.
3. **Rôles** : `registre`, `clerge`, `salarie`, `benevole`, `contact`, `fournisseur`, `association` (§5.2).
4. **Cumulables** : oui, `roles` est une liste.
5. **Relation** : un lien structuré vers une autre entité déjà modélisée (clocher, autre entrée d'annuaire) — jamais un rôle, traité au cas par cas (§5.3).
6. **Données d'identité** : nom/prénom ou raison sociale, coordonnées, notes, état civil (personne) — indépendantes de tout rôle (§5.4).
7. **Données de rôle** : tout ce qui n'existe que parce que ce rôle précis est actif (§5.5).
8. **Migration** : transformation par id préservé, pas de fusion automatique, doublons détectés puis fusionnés manuellement (§9).
9. **Tables Dexie nécessaires** : une seule nouvelle table, `directory` (§8).
10. **Modules à faire évoluer** : `people.js`/`personnel.js` (fusionnés ou retirés), `js/trash.js`, `js/search.js`, `js/diagnostics.js`, `js/settings.js` (DATA_MODULES), `js/core/backup.js`, `js/overview.js`, `js/main.js`, `js/state.js` (§4, §20).
11. **Historique/corbeille** : entrées existantes jamais réécrites, nouvelles entrées unifiées sous `directory`/`"directory"` (§10, §11).
12. **Import/export** : nouvelle clé `data.directory`, ancien format toujours lisible via reconstruction (§12).
13. **Recherche** : une seule source, résultats groupés par type/rôle (§13).
14. **Diagnostic** : étendu pour les rôles invalides, relations incohérentes, doublons inter-anciennes-tables (§14).
15. **Tests** : fonctions de transformation, helpers de rôle, extension des tests `detectBackupPayload`/diagnostic (§15).
16. **Risques principaux** : fusion automatique erronée, perte de champs libres non structurés, ampleur du chantier transverse (§17).
17. **Architecture recommandée** : table unique `directory`, rôles en objets, relations en champs id simples (§19).
18. **Plan V6.8** : trois sous-phases (fondations, module Annuaire, intégration transverse) — §20.
