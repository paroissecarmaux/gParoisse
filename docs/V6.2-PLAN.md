# Plan V6.2 — Données et intégrité

Statut : **planification uniquement, aucun code n'a été écrit.** À ne démarrer qu'après votre feu vert, un sous-groupe à la fois (voir « Ordre d'implémentation »).

Condition de démarrage (voir `docs/REVIEW-V6.0-V6.1.md`) : V6.1 est ✅ complet, aucune régression connue, `js/db.js` inchangé. V6.2 est donc en position de démarrer, **à condition** que vous ayez fait un tour manuel de l'application dans un navigateur au préalable (la seule vérification que je n'ai pas pu exécuter moi-même).

## Objectif V6.2

Réduire les risques d'incohérence de données déjà identifiés dans l'audit (références orphelines à la suppression, absence de traçabilité hors Demandes, absence de filet de rattrapage à la suppression, diagnostic d'import CSV trop pauvre) — sans toucher à la philosophie « simple, local, additif ».

## Fonctionnalités prévues

Regroupées en 3 sous-groupes indépendants (chacun livrable et testable séparément) :

### V6.2.a — Avertissement de suppression (pas de nouvelle version Dexie)
Avant `deletePerson`/`deleteClocher`/`deletePersonnel`, compter les enregistrements liés (`requests.personId`/`clocherId`, `intentions.personId`/`clocherId`/`personnelId`, `schedule.clocherId`) et l'afficher dans le texte de confirmation existant (« Cette personne est liée à 3 demandes et 1 intention ; le lien sera perdu. Continuer ? »). **Aucune donnée n'est modifiée** — l'enregistrement lié garde son `personId`/`clocherId` orphelin, l'affichage actuel (« Personne introuvable (supprimée) ») continue de le gérer côté lecture, comme aujourd'hui. Choix délibérément conservateur : ne pas toucher automatiquement à un enregistrement qui n'est pas celui qu'on supprime.

### V6.2.b — Rapport d'import CSV détaillé (pas de nouvelle version Dexie)
`importPeopleCSV` (`people.js`) et `importModuleCSVFile` (`settings.js`) collectent, pour chaque ligne ignorée, `{ligne, raison}` au lieu d'un simple compteur. Affichage : le toast agrégé actuel reste (« X importé(s) · Y ignorée(s) »), complété par une liste détaillée (dans une petite modale ou une zone dépliable, à définir avec vous — pas de nouveau composant lourd).

### V6.2.c — Historique généralisé + corbeille (nouvelle version Dexie v10)
- `HistoryRepository`/`addHistory`-équivalent appelé aussi depuis `savePerson`, `saveClocher`, `savePersonnel`, `saveIntention`, `saveSchedule` (aujourd'hui seul `requests.js` l'utilise).
- Champ `deletedAt` (nullable, absent par défaut = actif) ajouté à chaque table métier. `deleteX()` devient un « passage en corbeille » (`deletedAt = now`) ; une suppression définitive reste possible depuis une vue Corbeille dédiée, avec la même confirmation textuelle qu'aujourd'hui.

## Dépendances

- V6.2.a et V6.2.b sont indépendants l'un de l'autre et de V6.2.c.
- V6.2.c dépend de V6.1 (repositories déjà en place — `HistoryRepository` existe déjà et sera réutilisé tel quel).
- Aucune dépendance vers TypeScript, un backend, ou une dépendance externe nouvelle.

## Modifications DB éventuelles

- V6.2.a, V6.2.b : **aucune.**
- V6.2.c : `db.version(10)` — additive, comme toutes les précédentes :
  - `history` : ajout des champs `entityType`, `entityId` (les entrées déjà existantes pour les Demandes restent lisibles, traitées comme `entityType: "request"` par défaut à la lecture plutôt que migrées en base — pas de réécriture de données historiques).
  - `people`, `requests`, `schedule`, `clochers`, `personnel`, `intentions` : ajout du champ `deletedAt` (absent/`null` = actif, aucune valeur par défaut à écrire sur les enregistrements existants).
  - **Aucune version existante (5 à 9) n'est modifiée.**

## Modifications UI

- V6.2.a : texte de confirmation enrichi uniquement (pas de nouvel écran).
- V6.2.b : zone/modale de détail d'import (à valider avec vous avant de coder — je ne veux pas décider seul d'un nouveau patron d'UI).
- V6.2.c : une vue « Corbeille » par module (ou une vue unique filtrée par module, à trancher selon la préférence) + deux actions (Restaurer / Supprimer définitivement) sur chaque élément qui s'y trouve. Les listes existantes (Personnes, Demandes…) filtrent implicitement `deletedAt` absent, comme elles filtrent déjà `archived`/`active` aujourd'hui.

## Risques

- V6.2.a, V6.2.b : **faible** — aucun changement de schéma, changements de texte/affichage uniquement, réversibles instantanément.
- V6.2.c : **moyen** — nouvelle version Dexie (jamais neutre), nouveau concept transversal (corbeille) qui touche les 6 modules métier. Risque principal : oublier un endroit où un `deleteX()` doit devenir un passage en corbeille, ou une liste qui doit désormais exclure les éléments `deletedAt` renseigné. Mitigation : un module à la fois, un commit par module, rejouer `tests/pure-functions.test.js` après chaque étape (même s'il ne couvre pas encore la corbeille elle-même — l'étendre en même temps).

## Tests nécessaires

- Étendre `tests/pure-functions.test.js` avec les nouvelles fonctions pures introduites (ex. un éventuel `isDeleted(record)`/`entityTypeOf(record)` si de telles fonctions utilitaires sont créées).
- Test manuel obligatoire en navigateur pour V6.2.c avant diffusion : créer un enregistrement, le passer à la corbeille, vérifier qu'il disparaît des listes actives, le restaurer, vérifier qu'il réapparaît identique (mêmes champs, même id).
- Revérifier l'export/import JSON après V6.2.c : `deletedAt` doit être exporté/réimporté comme n'importe quel autre champ (aucune logique spéciale nécessaire si les repositories restent de simples enveloppes, mais à vérifier explicitement puisque le sens d'un enregistrement « supprimé mais encore en base » est nouveau).

## Ordre d'implémentation

1. V6.2.a (le plus rapide, le plus consensuel).
2. V6.2.b (indépendant, votre validation du patron d'UI avant de coder).
3. V6.2.c, module par module, dans cet ordre suggéré : `requests` (l'historique y existe déjà, sert de modèle) → `people` → `schedule` → `clochers` → `personnel` → `intentions`.

## Critères d'acceptation

- V6.2.a : le message de confirmation affiche un décompte exact et correct des enregistrements liés, sur un jeu de données réel comportant au moins un cas avec 0, 1 et plusieurs liens.
- V6.2.b : une ligne de CSV volontairement invalide (date manifestement fausse, colonne « nom » vide) apparaît nommément dans le rapport, avec un numéro de ligne correct et une raison compréhensible par un secrétariat non technique.
- V6.2.c : après passage en corbeille, l'enregistrement n'apparaît plus dans aucune liste/recherche/KPI actif ; après restauration, il réapparaît avec exactement les mêmes champs qu'avant (aucune perte, aucune duplication) ; après suppression définitive depuis la corbeille, il n'est plus récupérable et un nouvel enregistrement du même nom peut être créé sans collision d'id.
- Pour les trois sous-groupes : `tests/pure-functions.test.js` reste à 100 % de réussite, `js/db.js` diff limité aux ajouts additifs décrits ci-dessus (jamais de modification rétroactive d'une version existante).
