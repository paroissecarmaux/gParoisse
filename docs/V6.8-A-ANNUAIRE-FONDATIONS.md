## 4. Fonctions ajoutées

```js
// Transformations pures (js/core/directory.js)
personToDirectoryEntry(person) -> entry
personnelToDirectoryEntry(personnel) -> entry

// Helpers de lecture des rôles
hasRole(entry, roleType) -> bool        // au moins une instance ACTIVE de ce type
getRolesByType(entry, roleType) -> []   // toutes les instances (actives ou non)

// Migration
computeDirectoryMigration(existingDirectoryIds, peopleRecords, personnelRecords)
    -> { toCreate: [...], report: { createdFromPeople, createdFromPersonnel, skipped, warnings } }
    // Pure — ne touche pas Dexie, isolée pour rester testable (même
    // principe que detectBackupPayload(), V6.3).

async migratePeopleAndPersonnelToDirectory() -> report
    // Enveloppe Dexie : lit l'existant via les repositories, délègue le
    // calcul à computeDirectoryMigration(), écrit uniquement les
    // entrées nouvelles (bulkPut), journalise les avertissements
    // (Logger.warn) sans jamais bloquer le démarrage de l'app.

async loadDirectoryData()
    // state.directory = listActive(), state.directoryTrash = listDeleted()
    // — même patron que loadPeopleData()/loadPersonnelData().
```

**Décision explicite — sémantique de `hasRole()`** : répond à la présence d'au moins une instance **active** (`active !== false`) du rôle demandé, pas simplement sa présence historique. `getRolesByType()` couvre le besoin inverse (toutes les instances, actives ou non) quand le détail complet est nécessaire — par exemple pour lister les deux engagements bénévoles d'une même personne, l'un terminé et l'autre en cours.

**Décision explicite — `active`** : jamais déduit de `dateDebut`/`dateFin`. Pour les rôles dérivés de `personnel`, `active` recopie tel quel `personnel.active` (un signal explicite déjà existant). Pour les rôles dérivés de `people` (`registre`, `contact`), `active` vaut toujours `true` : `people` n'a aujourd'hui aucune notion d'archivage par personne (contrairement à `personnel.active`), donc rien ne justifierait une autre valeur — le décès éventuel reste porté par `dateDeces` au niveau de l'identité, pas par la désactivation du rôle (cohérent avec `docs/V6.7-ANNUAIRE-DESIGN.md` §5.4).

## 5. Structure exacte de `directory`

```js
// entityType: "person" (les deux seules sources de migration produisent ce type)
{
    id: "…",                  // conservé à l'identique depuis people.id ou personnel.id
    entityType: "person",
    prenom: "…", nom: "…",
    dateNaissance: "", lieuNaissance: "", dateDeces: "", pere: "", mere: "",   // identité (issu de people ; vide pour une entrée issue de personnel)
    telephone: "", email: "", adresse: "",
    notes: "…",                // notes existantes + role/groupe hérités (people) ou avertissement d'anomalie (personnel)
    roles: [
        {
            type: "registre",  // uniquement pour un people.profileType === "paroissien"
            active: true,
            rgpd: false,
            registre: "", lieuBapteme: "", diocese: "", anneeBapteme: "", numeroBapteme: "",
            dateBapteme: "", parrain: "", marraine: "", temoin: "",
            dateCommunion: "", lieuCommunion: "", dateConfirmation: "", lieuConfirmation: "",
            dateMariage: "", lieuMariage: "", conjoint: ""
        }
        // ou { type: "contact", active: true }
        // ou { type: "salarie", active, dateDebut, dateFin, fonction }
        // ou { type: "benevole", active, dateDebut, dateFin, domaine }
        // ou { type: "clerge", active, etatCanonique, dateDebut, dateFin }
        // — une entrée personnel peut cumuler salarie/benevole ET clerge (2 objets)
    ],
    migratedFrom: "people" | "personnel",   // provenance temporaire, voir §7
    createdAt: "…", updatedAt: "…", deletedAt: null

```

`entityType: "organization"` est un état valide du modèle (accepté par le schéma, par `DIRECTORY_ENTITY_TYPES`) mais **aucun code n'en produit** dans cette sous-phase — confirmé, aucune organisation n'existe dans le dépôt à l'issue de V6.8.a.

## 6. Stratégie de migration

- **Une entrée `people`/`personnel` → une entrée `directory`, même `id`.** Jamais de `uid()` généré pour une entrée migrée (vérifié par test : `id conservé à l'identique`, x2).
- **Aucune fusion.** Une personne présente à la fois dans `people` et `personnel` (le cas exact que l'Annuaire doit résoudre à terme) produit **deux entrées distinctes** dans `directory` — pas de rapprochement automatique par nom, jugé trop risqué (homonymes). La détection de ce genre de doublon reviendra au diagnostic d'intégrité, étendu en V6.8.c (prévu dans `docs/V6.7-ANNUAIRE-DESIGN.md` §9.1, pas fait ici).
- **Rôles dérivés sans invention** : `profileType`/`typeEngagement`/`etat` pilotent strictement quels rôles apparaissent ; aucune valeur par défaut arbitraire n'est ajoutée quand rien ne permet d'en déduire un (voir cas `roles: []` ci-dessous).
- **Cas `roles: []`** (`personnel` avec `typeEngagement` non reconnu ET `etat` absent/"Laïc") : ne déclenche **aucun** rôle de repli. `computeDirectoryMigration()` l'ajoute à `report.warnings` (journalisé via `Logger.warn("directory.migration", …)` au démarrage, jamais silencieux) ; les données brutes non interprétées (`typeEngagement`, `etat`, `fonction`) sont conservées dans `notes` de l'entrée migrée pour qu'aucune information ne se perde. L'entrée `directory` est tout de même créée (pas exclue de la migration) — juste signalée comme à corriger manuellement.
- **`people.role`/`people.groupe`** (texte libre existant, jamais structuré) : conservés tels quels dans `notes`, étiquetés explicitement (`"Rôle (ancien champ libre) : …"`), jamais transformés en rôle structuré.

## 7. Champ de provenance temporaire

`migratedFrom: "people" | "personnel"` — ajouté pour faciliter le diagnostic pendant V6.8.b/c (permet de savoir d'où vient une entrée sans deviner à partir de ses rôles). **Explicitement documenté comme temporaire** : n'apparaît pas dans le modèle fonctionnel cible de `docs/V6.7-ANNUAIRE-DESIGN.md`, à retirer si V6.9 confirme qu'il n'est plus utile une fois la bascule stabilisée. N'est ni indexé, ni obligatoire, ni lu par aucun code de validation.

## 8. Stratégie d'idempotence

`migratePeopleAndPersonnelToDirectory()` lit l'ensemble des `id` déjà présents dans `directory` (`DirectoryRepository.list()`) **avant** toute écriture, puis délègue à `computeDirectoryMigration()` (pure) qui **ignore** toute entrée `people`/`personnel` dont l'`id` existe déjà côté `directory` — jamais recréée, jamais réécrite, même si la fiche source a changé depuis. Conséquences :

- Une exécution répétée (à chaque démarrage de l'app) ne duplique rien : vérifié par le test `seconde exécution -> aucune duplication`.
- Une modification faite plus tard directement sur une entrée `directory` (via une future interface V6.8.b) n'est **jamais écrasée** par une migration ultérieure — la migration ne s'intéresse qu'aux `id` absents.
- Une nouvelle fiche créée dans `people.js`/`personnel.js` (toujours actifs pendant cette phase) après la première migration est reprise automatiquement au prochain démarrage — `directory` reste à jour sans action manuelle.
- **Pas de transaction Dexie** pour cette écriture : une exécution partielle (ex. le navigateur se ferme au milieu du `bulkPut`) ne laisse pas d'état incohérent au sens strict — les entrées non créées seront simplement retentées, sans risque, au prochain démarrage, précisément parce que l'idempotence par `id` rend l'opération auto-réparatrice. Choix cohérent avec la consigne de ne pas ajouter de complexité non nécessaire à cette sous-phase.

## 9. Tests ajoutés et exécutés

30 nouveaux tests, répartis exactement selon les catégories demandées :
- `personToDirectoryEntry` : paroissien complet (rôle registre + champs sacramentaux), contact, RGPD (avec/sans consentement), `role`/`groupe` conservés en notes, personne supprimée (`deletedAt`), id conservé — **6 tests**.
- `personnelToDirectoryEntry` : bénévole, salarié, prêtre, diacre, religieux(se), laïc (aucun clerge), engagement + clergé cumulés, entrée inactive, entrée supprimée, id conservé, aucun rôle déterminable (cas anomalie) — **11 tests**.

- `computeDirectoryMigration` : ensemble vide, `people` seul, `personnel` seul, les deux combinés (id conservés), `deletedAt` conservé, avertissement sur rôle non déterminable, seconde exécution sans duplication — **7 tests**.

Aucune régression : les 78 tests déjà présents avant cette sous-phase passent toujours à l'identique.
