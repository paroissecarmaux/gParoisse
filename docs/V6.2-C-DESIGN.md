## 7. Toutes les fonctions d'export — impact de `deletedAt`

`exportJSON()` (`settings.js:284`) et `exportModuleCSV()` (`settings.js:319`) exportent `state[m.stateKey]` intégralement, via le registre `DATA_MODULES`. **Aucun changement de code n'est nécessaire** pour que `deletedAt` soit exporté : c'est un champ comme un autre, il sera inclus automatiquement. Décision à prendre : faut-il l'exporter (recommandé — une sauvegarde doit refléter l'état réel, corbeille comprise, pour permettre une restauration fidèle) ou l'exclure (déconseillé — on perdrait l'information de corbeille au moindre export/réimport) ? **Recommandation : l'exporter tel quel**, sans traitement spécial.

Ajout nécessaire : une entrée `{ key: "deletedAt", header: "Supprimé le", type: "date" }` dans chaque `csvFields` de `DATA_MODULES`, pour que l'export/import CSV (pas seulement JSON) préserve aussi cette information.

## 8. Toutes les fonctions d'import — impact de `deletedAt`

`importFile()` (JSON, `settings.js:409`), `importModuleCSVFile()` (CSV générique, `settings.js:335`), `importPeopleCSV()` (CSV registre, `people.js:640`). Les trois passent par `m.normalize()`/construction d'objet — **aucun changement structurel requis** si `deletedAt` est un champ optionnel de plus : un enregistrement importé sans ce champ sera traité comme actif (comportement par défaut), un enregistrement importé avec `deletedAt` renseigné sera considéré en corbeille dès son import. C'est cohérent et ne casse rien pour les sauvegardes antérieures à V6.2.c (elles n'ont simplement jamais ce champ, donc tout redevient actif à la réimportation — comportement raisonnable par défaut, à confirmer avec vous).

## 9. Toutes les relations croisées — que se passe-t-il si une entité est en corbeille ?

Scénario à trancher explicitement (aucune décision prise ici, seulement les options) :

- **Une Personne passe en corbeille alors que des Demandes/Intentions la référencent** : ces Demandes/Intentions restent actives, mais leur lien devient un lien vers une fiche « cachée ». Aujourd'hui (sans corbeille), `showRequestDetail()`/`showIntentionDetail()` font `state.people.find(p => p.id === r.personId)` — si `state.people` (une fois filtré par défaut pour exclure la corbeille) ne contient plus cette personne, `linkedPerson` devient `null`/`undefined` et l'affichage bascule automatiquement sur le texte de repli déjà existant (« Personne introuvable (supprimée) ») — **sans changement de code**, à condition que `state.people` lui-même soit filtré une fois pour toutes au chargement (`loadPeopleData()`) plutôt que dans chaque fonction consommatrice. C'est un argument fort pour centraliser le filtre `deletedAt` dans les `loadXData()` plutôt que de le disperser (voir point suivant).
- **Un Clocher/Personnel en corbeille référencé par une Demande/Annonce/Intention active** : même raisonnement, même filet de sécurité déjà en place.
- **Restaurer une Personne dont une Demande la référence toujours** : le lien redevient automatiquement valide (puisque `personId` n'a jamais été touché, conforme à la décision V6.2.a de ne jamais modifier les enregistrements liés).

## 10. Historique — structure minimale proposée

Proposition de la roadmap : `entityType`, `entityId`, `action`, `createdAt` (+ `description` déjà existant). **Suffisante**, à une nuance près : `action` devrait rester une valeur fermée (`"create" | "update" | "archive" | "restore" | "trash" | "untrash" | "purge" | "complete" | "delete"` — la liste actuelle dans `requests.js` utilise déjà `"create"/"update"/"archive"/"restore"/"complete"/"delete"`) plutôt qu'un texte libre, pour rester exploitable plus tard (filtrer l'historique par type d'action).

**Anciennes entrées `history`** (déjà en base, uniquement pour les Demandes, sans `entityType`/`entityId`) : ne pas les migrer en base (la mission l'interdit de toute façon — aucune modification rétroactive de données). À la lecture, un enregistrement `history` sans `entityType` est traité comme `entityType: "request"` par défaut (son seul type possible historiquement), en gardant `entityId = requestId` tel quel (le champ `requestId` reste présent, simplement plus utilisé pour les nouvelles entrées qui utiliseront `entityId`).

## Convention centralisée `isActive`/`isDeleted`

**Recommandation : oui, à créer avant d'écrire la moindre condition `!record.deletedAt` dispersée.** Proposition minimale, dans `js/utils.js` (à côté de `countByField` etc., même esprit — petites fonctions pures) :

```
function isDeleted(record) { return Boolean(record?.deletedAt); }
function isActive(record) { return !isDeleted(record); }
```

Et, dans chaque repository (`repositoryFactory.js`), deux méthodes supplémentaires opérant sur le résultat de `list()` (pas une nouvelle requête Dexie — cohérent avec le fait que `deletedAt` n'est pas indexé, on ne veut pas changer le schéma pour ça) :

```
listActive: async () => (await list()).filter(isActive),
listDeleted: async () => (await list()).filter(isDeleted),
```

Chaque `loadXData()` appellerait alors `XRepository.listActive()` au lieu de `XRepository.list()` — **un seul point de filtrage par module**, plutôt que de disperser `!x.deletedAt` dans 6 `renderXList`, 6 `renderXSummary`, 3 `xSuggestions`, 5 sources de `search.js`, et l'agrégation `overview.js`/`agenda.js`. La vue Corbeille, elle, appellerait `XRepository.listDeleted()` pour peupler sa propre liste séparée. C'est exactement le genre de dispersion que vous avez demandé d'éviter, et centraliser au niveau du chargement (plutôt qu'au niveau de chaque consommateur) est le point unique le plus sûr.

## Corbeille — analyse détaillée

- **Passage en corbeille** : `record.deletedAt = nowISO(); await XRepository.put(record);` — jamais de suppression Dexie réelle à cette étape.
- **Restauration** : `record.deletedAt = null; await XRepository.put(record);` — **même `id`, mêmes champs, aucune recréation** (conforme à l'exigence : l'ID original doit être conservé). Puisque `put()` avec le même `id` fait un remplacement complet de l'enregistrement Dexie (comportement Dexie standard), et que le reste de l'objet n'a jamais été modifié entre la mise en corbeille et la restauration, l'enregistrement restauré est **identique bit à bit** à son état juste avant la mise en corbeille, hormis `deletedAt` lui-même.
- **Suppression définitive** : uniquement possible depuis une entrée déjà en corbeille (garde-fou UI : le bouton « Supprimer définitivement » n'apparaît que sur la vue Corbeille) → `XRepository.remove(id)` (le vrai `db.table.delete()` déjà existant).
- **Relations** : voir point 9 — aucun impact sur les enregistrements liés, dans aucun des trois cas.
- **Recherche/listes/export/import/KPI** : voir points 4 à 8.
- **IDs/doublons** : aucun risque nouveau — l'`id` ne change jamais pendant tout le cycle Actif → Corbeille → Restauré, ou Actif → Corbeille → Supprimé définitivement (l'id est alors libéré, une future création avec `uid()` ne le régénérera jamais puisque `uid()` est un UUID aléatoire, pas séquentiel).

## Transactions Dexie — recommandation

La revue V6.0/V6.1 a confirmé qu'aucune transaction explicite n'existe nulle part dans le projet (chaque écriture — demande, historique — est indépendante). Pour V6.2.c, les opérations composites concernées seraient : *mise en corbeille + entrée d'historique*, *restauration + entrée d'historique*, *suppression définitive + entrée d'historique*.

**Recommandation : ne pas introduire de transaction Dexie explicite pour V6.2.c.** Raisons :
1. C'est un changement d'ampleur pré-existant (déjà vrai avant V6.2.c pour `saveRequest` + `addHistory`, jamais transactionnel) — l'introduire seulement pour la corbeille créerait une incohérence de rigueur entre fonctionnalités similaires.
2. Le risque réel est faible en usage mono-utilisateur local (pas de concurrence entre onglets/appareils à gérer) : si l'écriture d'historique échoue juste après une mise en corbeille réussie, l'enregistrement est bien en corbeille (donné correct) mais sans trace ; ce n'est pas une incohérence de *données métier*, seulement une lacune d'audit.
3. Ajouter des transactions Dexie (`db.transaction("rw", db.X, db.history, async () => {...})`) reste **possible plus tard, sans casser l'existant**, si un besoin réel de cohérence stricte apparaît (ex. audit légal). Ce n'est pas un choix irréversible qu'il faut trancher maintenant.

Si vous préférez la rigueur immédiate malgré le faible risque, la transaction pourrait être ajoutée en un point unique et réutilisé par les 6 modules (`js/core/` semble le bon endroit), sans complexité disproportionnée — mais ce n'est pas ma recommandation par défaut.
